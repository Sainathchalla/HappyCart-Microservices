General Flow => User(Browser) -> Gateway -> Resources

-> This is the usual flow without security.
-> If we want to secure APIs, we use Spring Security as the security framework.
-> We are using KeyCloak an open source IAM tool (Identity and Access Management).
-> Spring Security implements OAuth2 / OpenID Connect in our application.
-> Keycloak is the OAuth2 Authorization Server.

Stack ->
Spring Security → security framework
OAuth2/OpenID Connect → security protocol
Keycloak → authorization server implementation



Process of Authentication and Authorization.

-> First we should have KeyCloak Setup which should have all the info about clients, users etc.

Step-1:  Browser(User) -> Gateway

-> Gateway is configured as security guard for our entire system.
-> Gateway sees No access token present in the request.
-> So, Gateway responds: Redirect to Keycloak login.

Step-2: Browser -> Keycloak

-> So, Browser goes to Keycloak
-> Here Authorization Server is KeyCloak, now we enter keycloak verification stage, where you need to provide your credentials and KeyCloak verifies those.
-> Once verified, it will give you Access Token, Refresh Token, ID Token to the browser. All these are stored in browser.
-> Access Token = Used for API calls
-> Refresh Token = Used to get new Access and Refresh Token, when current access token expires
-> ID Token = Has User Information


Step-3: Browser(Access Token) -> Gateway

# Here there might be 2 possibilities:
a) JWT token validation done in Gateway itself
b) Again a network call is made to Keycloak for introspection, to know that the token really given by KeyCloak

# How Gateway extracts information from JWT token is by libraries which are in Spring Security.
# Spring Security also extracts User, Roles, Permissions from the token.

-> Gateway sees the token. Which is a JWT. JWT has Header, Payload and Signature.
-> Gateway need to validate the token locally. Validation includes: Verify JWT signature, Check expiry, Check issuer.
-> First question Gateway should ask whether this token is really given by Keycloak? For that we need to see the Signature right.
-> Private key creates the Signature, Public key verifies the signature.
-> Now Gateway requests for public key from Keycloak, it downloads the JSON which then converted to public key using Spring Security.
-> Verifies the signature using the public key. If it matches, then we are sure that it is signed by Keycloak.
-> If token is valid and not expired, then request is delegated to the appropriate microservice.



Step-4: Gateway -> Microservice
-> Now Gateway forwards this request to the appropriate microservice along with Access Token.
-> Now the microservice also can re-verify the JWT locally if wanted by using spring security.

Step-5: Microservice -> Gateway -> User.
-> Here you see, User never talks to the Microservice directly, because Gateway sits in between and hides Microservice. So Gateway is also called as reverse proxy.
-> Gateway acting like a proxy for the microservices(servers). User are talking to gateway, but gateway actually forwarding those to microservices.
| Type          | Who is being represented |
| ------------- | ------------------------ |
| Proxy         | Client                   |
| Reverse Proxy | Server                   |
